# Research

This document backs up the claims in the [README](../README.md) and the design choices in [ARCHITECTURE.md](ARCHITECTURE.md). It was written before any code, per the project's own ground rule: research first, build second.

## Origin of the idea

The concept came from a set of tutorial screenshots pitching an AI system for flower-auction buyers: photograph a flower, instantly get its species, quality, and price. The tutorial's own architecture and tech-stack diagrams (a "Multimodal RAG System" using Gemini Pro Vision, a vector database of botanical taxonomy, and a RAG pipeline into "FloraHolland's Real-time Pricing API") are the direct basis for this project's planned pipeline. Everything below is independent verification of the claims and technologies that pitch relied on.

## FloraHolland

Royal FloraHolland's Aalsmeer auction is the world's largest flower market.

- On a typical weekday, **~43 million flowers and 5 million plants** change hands. [Air Cargo Week](https://aircargoweek.com/aalsmeer-the-beating-heart-of-global-flower-trade/)
- The facility spans **35 auction clocks** and trades **30,000+ species and varieties** of flowers and plants, across a site of nearly **1 million square metres**. [Visit Aalsmeer — official facts page](https://www.visitaalsmeer.nl/en/facts-flower-auction-aalsmeer/)
- **~60% of the world's flower and plant trade** flows through Dutch auctions; Royal FloraHolland alone accounts for ~54% of everything sold in the Netherlands. [Air Cargo Week](https://aircargoweek.com/aalsmeer-the-beating-heart-of-global-flower-trade/)
- The auction traces back to 1910. [Air Cargo Week](https://aircargoweek.com/aalsmeer-the-beating-heart-of-global-flower-trade/)

**Why this matters for the project**: this confirms the "43 million flowers daily" claim from the tutorial screenshots is accurate (not a rounded-up marketing number), and grounds the core problem statement — at that volume and speed, manual species/quality/price verification per lot is not realistic. It also confirms **FloraHolland does not publish a public real-time pricing API** — no such API turned up in search, and their pricing/clock data is understood to be a closed, internal auction system for member growers and buyers. This is why BloomLens uses clearly-labeled **simulated** pricing rather than claiming a live integration.

## Museum of the Future, Dubai — "The Library"

The plant-scanner reference in the tutorial screenshots is "The Library," an installation at Dubai's Museum of the Future.

- It holds **2,400 crystal specimen jars**, suspended across a 375 m² space, each laser-etched with an existing or extinct lifeform. [The National](https://www.thenationalnews.com/uae/2022/02/23/five-stunning-displays-inside-dubais-museum-of-the-future/)
- Visitors use a **handheld scanning device** ("bio-synth," designed by the UK experiential-art collective Marshmallow Laser Feast) to scan a jar and pull up that species' history and conservation status on a screen. [Superflux](https://superflux.in/index.php/work/the-vault-of-life-in-museum-of-the-future/), [The National](https://www.thenationalnews.com/uae/2022/02/23/five-stunning-displays-inside-dubais-museum-of-the-future/)
- The catalogue spans a wide range of life forms, from trees to animals, not flowers specifically.

**Why this matters for the project**: this is the direct inspiration for the "photo in → instant info card out" interaction, but it's a physical museum exhibit with custom hardware. BloomLens borrows the *interaction pattern* only — a web app where a photo stands in for the physical scan — and makes no claim of using or replicating the museum's actual hardware or software.

## BioCLIP and BioCLIP 2

The tutorial's "Vector Database (Botanical Taxonomy – 100K+ Species Embeddings)" component maps closely onto real, open-source research:

- **BioCLIP** (CVPR 2024, Oral, **Best Student Paper**) is a CLIP-style vision foundation model trained on **TreeOfLife-10M** — 10M+ images spanning **454,000 taxa** — for hierarchical taxonomic classification (Kingdom → Phylum → Class → Order → Family → Genus → Species). It outperformed prior baselines by 16–17 percentage points on fine-grained biological classification. [CVPR Open Access](https://openaccess.thecvf.com/content/CVPR2024/html/Stevens_BioCLIP_A_Vision_Foundation_Model_for_the_Tree_of_Life_CVPR_2024_paper.html), [GitHub](https://github.com/Imageomics/bioclip), [paper](https://arxiv.org/abs/2311.18803)
- **BioCLIP 2** (NeurIPS 2025, Spotlight) supersedes it, trained on **TreeOfLife-200M** (214M+ images), with further gains on tasks like habitat classification and trait prediction. [Imageomics announcement](https://imageomics.osu.edu/news/2025/07/branching-out-bioclip-2-pushes-boundaries-ai-nature), [HuggingFace](https://huggingface.co/imageomics/bioclip-2), [paper](https://arxiv.org/pdf/2505.23883)
- Both are freely downloadable: model weights on HuggingFace (`imageomics/bioclip`, `imageomics/bioclip-2`), plus a `pybioclip` Python package for straightforward inference.

**Why this matters for the project**: the tutorial's vector-database idea doesn't have to be a toy lookup table — it can be built on a real, citable, state-of-the-art research model that already does exactly this kind of taxonomic embedding. This is the single biggest upgrade this research pass makes to the original pitch: BioCLIP 2 embeddings + a Qdrant index *are* the "botanical taxonomy vector database," at whatever species-count scope the demo needs.

### What's actually in the paper (full read, not just the abstract)

Having gone back and read the full BioCLIP paper (not just the abstract and Figure 1 shown in the tutorial screenshots), a few details directly shape the design:

- **How classification actually works**: BioCLIP flattens the 7-level taxonomy (Kingdom → Species) into one string — e.g. `"Plantae Tracheophyta Magnoliopsida Rosales Rosaceae Rosa gallica"` — wrapped in a CLIP-style template (`"a photo of {taxonomic name}"`), and encodes it with a 77-token causal text encoder. An image is classified by embedding it with the ViT-B/16 vision encoder and finding the taxonomic-name text embedding it's closest to by cosine similarity. **This means species ID doesn't require a database of reference photos at all** — just text embeddings of the candidate species' taxonomic names. That changes the vector-DB design (see [ARCHITECTURE.md](ARCHITECTURE.md)): Qdrant stores taxonomy-string embeddings, not reference images.
- **Plant accuracy is genuinely strong**: on the PlantNet benchmark, BioCLIP scores **91.4% zero-shot** accuracy (no fine-tuning, no examples) — one of its best results across all 10 evaluation tasks, ahead of birds (72.1%), insects (34.8%), and fungi (40.7%). This is a real, measured number, not marketing — it's good evidence this approach will work for flower species specifically.
- **It is measurably weak at disease/condition classification**: on PlantDoc (leaf disease detection) it scores only 28.4% zero-shot, and PlantVillage 24.4% zero-shot (rising to 80.9% only with 5-shot fine-tuning). The paper's own conclusion: BioCLIP is trained on a *species*-classification objective, which limits its use for non-taxonomic traits. **This directly confirms the plan to keep "quality" assessment (freshness, wilting, blemishes) out of BioCLIP's hands and let Gemini's vision-language reasoning handle it instead** — the underlying model was never built for that task.
- **Ablations show the CLIP contrastive objective matters a lot**: a plain cross-entropy classifier over taxonomy got 16.7% mean 1-shot accuracy vs. 45.1% for the CLIP-style objective — a >2x gap. This is why "just fine-tune a classifier" is a materially worse approach than using BioCLIP's own embedding space.
- **Known limitation relevant to cut flowers**: the paper flags that common names don't map 1:1 to species, and that its source data (iNat21, EOL, BIOSCAN-1M) skews toward wild/citizen-science-photographed organisms. It says nothing about performance on cultivated ornamental *cultivars* (e.g. distinguishing a specific commercial rose variety) — that's an untested gap, not a claim either way. Practically: expect BioCLIP to nail genus/species (e.g. "this is a rose, *Rosa*") reliably, but treat cultivar-level distinctions as beyond what's been validated.

## Correction: Gemini model naming and quota, and API key format

The tutorial's tech-stack diagram names `gemini-pro-vision` as the image-recognition model. That model name is long deprecated — Gemini has moved through the 1.5, 2.x, and (as of September 2026) 3.x Flash generations. Two things learned building Milestone 1, worth recording since they cost real debugging time:

- **The `-latest` alias is not always the safe choice, and the 20-req/day quota isn't unique to one model.** `gemini-flash-latest` currently resolves to `gemini-3.8-flash`, released days before this was built, capped at **20 requests/day per project** — far below the ~1,500/day some older Flash generations reportedly get. BloomLens pinned to `gemini-3.6-flash` (`src/identify.py`) expecting more headroom, but hit the *same* 20/day cap during Milestone 2 testing — so this project/key's free tier appears to cap every current 3.x-generation **Flash** model at 20/day, not just the newest one. The retry-after hint on the 429 (~20-30s, not hours) suggests it behaves more like a slow-refilling rate limit than a hard once-a-day wall.
- **Milestone 3 made this a real blocker, not just a curiosity.** Once `identify()` became an agent that reasons across several tool-calling round-trips (`lookup_taxonomy` → `assess_quality` → `check_price` → final answer — 4+ Gemini calls per single scan, confirmed by inspecting the agent's message trace), `gemini-3.6-flash`'s 20/day cap meant **roughly 4-5 total scans per day** before the whole app stopped working — plus a *separate*, tighter **5-requests/minute** cap that a single multi-call `identify()` invocation can trip on its own. Switched `_GEMINI_MODEL` to **`gemini-3.1-flash-lite`** (a named, verified version — not another `-latest` alias) after confirming empirically it tracks a completely separate quota bucket from the Flash line and has real headroom for this workload. Lesson generalized: for an agentic design specifically, budget quota per *identify() call*, not per Gemini model call — the multiplier is real and easy to undercount, and Google's "efficient/workhorse" tier (Flash-**Lite**) currently keeps the generous free quota that flagship Flash models have lost.
- **API keys changed format in 2026.** Keys now start with `AQ.` rather than the historical `AIzaSy...` — the SDK (`google-genai>=2.22.0`) handles this transparently, but anything assuming the old prefix (including outdated advice, possibly including earlier turns of this very project's own planning) will incorrectly reject a valid key.
- **Gemini's structured-output feature (`response_schema`/`response_json_schema`) returned intermittent 503s** in testing — a known, currently-open SDK issue ([googleapis/python-genai#1378](https://github.com/googleapis/python-genai/issues/1378)). Plain-text generation with a prompt-requested JSON format, parsed manually, was reliable; see `src/identify.py`.

## Correction: `requirements.txt` had a latent, undetected dependency conflict

Building the Milestone 7 Docker image (a genuinely *fresh* `pip install -r requirements.txt`, no prior environment state) failed immediately with `ResolutionImpossible`: `pydantic==2.10.3` (pinned since Milestone 1) conflicts with `google-genai==2.22.0`'s own requirement of `pydantic>=2.12.5` (added in Milestone 3). This had been silently true in the local dev venv since Milestone 3 — installing `google-genai`/`langchain` there via incremental `pip install <package>` calls quietly upgraded pydantic to `2.13.5` to satisfy the real constraint, without ever touching or re-validating `requirements.txt`'s stale `2.10.3` pin. `pip install -r requirements.txt` was never run again as a *whole* after that, so nothing surfaced the mismatch — until Docker's clean build forced a full resolve from the file's own numbers, not the venv's actual (already-patched) state. This means the CI `lint-and-eval` job would also have failed on this exact conflict, since it does the same fresh install. Fixed by re-pinning to `pydantic==2.13.5` (verified via `pip install --dry-run -r requirements.txt` before the Docker rebuild). General lesson: an incrementally-patched local venv can mask a `requirements.txt` that's actually broken for anyone (or any CI/Docker build) starting fresh — worth periodically validating the pinned file in isolation, not just trusting that "it works on my machine."

## Correction: CI's first real run caught a second fresh-checkout gap

Pushing Milestone 7 and actually watching the GitHub Actions run (rather than assuming a workflow file that *looks* right *is* right) surfaced a second, different fresh-environment bug: `eval/run_eval.py` failed with `ValueError: Collection species_taxonomy not found`. `qdrant_data/` is (correctly) gitignored — it's generated by `scripts/build_index.py`, not source — but every local run of the eval harness so far had an already-populated `qdrant_data/` sitting around from earlier milestones' work, so this dependency was never actually exercised. The CI workflow's `lint-and-eval` job ran `ruff check .` then jumped straight to `eval/run_eval.py`, never calling `scripts/build_index.py` first — something a persistent local dev environment will never expose on its own. Fixed by adding a "Build the local Qdrant index" step before the eval step, and verified the fix for real by temporarily moving the local `qdrant_data/` aside to simulate a fresh checkout, confirming the same 87.2%/96.1% result. `docker-smoke-test` (the other CI job) passed on the very first push — its `build-index` service already had this exact ordering right, since Docker Compose's `depends_on` made the sequencing explicit there; the plain CI job had no equivalent structural forcing function, which is exactly how the gap slipped through initially.

## Hugging Face Spaces (Docker SDK) — researched for Milestone 8

Before designing the live-demo deployment, fetched HF's own Docker Spaces docs directly rather than assuming a generic Dockerfile would work as-is:

- A Docker Space needs a `README.md` with YAML frontmatter (`sdk: docker`, `app_port`, title/emoji/colors) at the root of **the Space's own git repo**. [HF Docker Spaces docs](https://huggingface.co/docs/hub/en/spaces-sdks-docker)
- The container runs as **uid 1000, not root** — HF's own documented pattern is `useradd -m -u 1000 user` plus `COPY --chown=user` before installing/downloading anything.
- Free-tier Spaces have an **ephemeral filesystem**: disk writes are lost on every restart (including waking from sleep) unless a paid Storage Bucket is attached. Secrets set in a Space's Settings are injected as plain runtime environment variables — `os.environ.get(...)` in application code needs no change to read them.
- **Checked, not assumed: does GitHub render YAML frontmatter specially, the way HF does?** No — confirmed by search that GitHub's markdown renderer does not parse or strip frontmatter in a plain repo README; a `---`/YAML/`---` block at the top would render as a literal horizontal rule followed by plain-text `key: value` lines. This directly shaped the design: the Space cannot reuse this project's polished root `README.md` (or the Compose-oriented root `Dockerfile`, which runs as root and defers weight downloads to first run) without either uglifying the GitHub README or fighting the Compose setup's own, deliberate Milestone-7 choices. See `docs/ARCHITECTURE.md`'s "Deployment: Hugging Face Spaces" section for the resulting design (a separate `Dockerfile.hf` / `README.hf.md`, deployed via `scripts/deploy_hf_space.py`).

## Grad-ECLIP: interpretability for a zero-shot ViT, not literal Grad-CAM

Milestone 9's interpretability overlay started from a documented open question: is a "Grad-CAM-style" overlay literally Grad-CAM here? Checked directly against the loaded model rather than assumed from BioCLIP 2's name:

- `model.visual` is `open_clip.transformer.VisionTransformer` — ViT-L/14, 224×224 input, 16×16=256 patch grid, 24 transformer blocks, standard CLS-token pooling. **No convolutional feature maps** past the patch-embedding stem, and **no classifier head** — classification is cosine similarity between the image embedding and a candidate's text embedding (zero-shot). The original Grad-CAM paper needs both a conv feature map and a class score to backprop — BioCLIP 2 has neither, so the literal technique has nowhere to attach.
- Each block's attention is a plain `torch.nn.MultiheadAttention` with **`need_weights=False` hardcoded** in `open_clip.transformer.ResidualAttentionBlock.attention` — confirmed by reading the installed package's actual source (`inspect.getsource`), not assumed. Attention weights are never materialized on a normal forward pass.

**Technique used instead: Grad-ECLIP** — "Gradient-based Visual Explanation for Transformer-based CLIP" (Zhao et al., ICML 2024; [arXiv:2502.18816](https://arxiv.org/html/2502.18816)) — a published method for exactly this case (a CLIP-style ViT dual-encoder doing similarity-based zero-shot matching). Their own ablation found using only the **last** transformer layer gives the highest fidelity for images (lower layers "include less semantic information and may introduce more noise") — also the simplest version to implement, not a corner cut.

**Verified the actual formula against the paper's own reference implementation** ([github.com/Cyang-Zhao/Grad-Eclip](https://github.com/Cyang-Zhao/Grad-Eclip), `generate_emap.py`) rather than trusting a paraphrased summary — worth doing, because the paraphrase and the real code disagreed on a detail that mattered (see below). Core formula, per patch *i*: `H_i = ReLU(cosine(q_cls, k_i) · Σ_c grad_cls[c] · v_i[c])`, where `grad_cls` is the gradient of the image-text cosine similarity w.r.t. the CLS token's last-layer attention output.

**Three real bugs found and fixed by comparing a first implementation attempt against that reference code (and against the codebase's own established concurrency lessons), not by guessing:**
1. **Wrong basis for the dot product.** First attempt took the gradient w.r.t. `nn.MultiheadAttention`'s own returned output (already passed through `out_proj`) and dotted it against the raw value vectors `v` (a different, pre-`out_proj` basis). Produced heatmaps concentrated on background bokeh, not the photographed flower — a real, visible failure, not a subtle numerical error. The reference implementation's `attn_output` is explicitly *pre*-`out_proj` (`clip_encode_dense`'s own manual attention computation, `out_proj` applied separately afterward) — the same basis the value vectors live in.
2. **Missing normalization.** The reference's `cosine_qk` (the CLS→patch spatial term) is explicitly min-max normalized to `[0, 1]` before use — the initial paraphrase summary of the paper omitted this. Without it, the narrow raw-cosine value range washed out the real spatial signal.
3. **A thread-safety bug in the fix for #1, caught before shipping.** Since `nn.MultiheadAttention` doesn't expose the pre-`out_proj` tensor via a hook, the first working version of fix #1 monkey-patched `ResidualAttentionBlock.attention` (the last block's bound method) for the duration of one explain call. That method lives on `model.visual` — a process-wide singleton (`src/embeddings.py`'s `load_model()`), the exact same kind of shared, stateful object whose local/embedded-mode file lock caused a real bug in Milestone 1, and whose Docker Compose concurrency Milestone 7 had to design around. A concurrent `identify()`/`embed_image()` call on another thread (Streamlit and FastAPI's sync handlers can both serve concurrent requests, per Milestone 6) could have been routed through the patched method mid-flight, or had the patch torn down underneath it. Fixed by manually unrolling only the last block's computation from its own weights instead of patching anything — every tensor is local to one call, nothing shared is ever mutated. Verified with a real concurrent-call test (`explain_image` and `embed_image` firing from multiple threads at once, no corruption).

Also found a smaller but genuinely misleading issue in the *display*, not the math: a flat single-hue (red) overlay was illegible on already-red/orange flowers (Rose, Carnation) — the tinted photo looked no different in the already-warm regions regardless of the heatmap's actual values there, and a plain grayscale side-by-side was needed to confirm the underlying computation was actually correct before concluding the colormap itself was the problem. Switched to a hand-rolled cool(blue)→warm(red) 3-stop gradient, which stays legible regardless of the photo's own colors.

**No ground-truth metric exists for this project's flower photos** to score heatmap correctness against (unlike the species-ID evaluation harness's labeled test set) — verification here is necessarily by eye: does the heatmap land on the flower and shift when explaining a different candidate species. Confirmed on real photos from `eval/test_images/` (Amaryllis, Sunflower, Rose, Carnation) before shipping.

## SQLite WAL mode for the inventory log's multi-process writes

Milestone 10's persistent inventory log needed the same question Milestone 1 and Milestone 7 already answered once for Qdrant: what happens when more than one process writes to a local, file-based store at once? Docker Compose runs `web` and `api` as separate containers/processes, both of which log a row on every successful scan — the exact scenario that made Qdrant's local/embedded mode's exclusive file lock a real bug in Milestone 1.

SQLite's *default* journal mode (rollback journal) has the same class of risk: a writer takes an exclusive lock that blocks readers for the duration of a transaction. **WAL (write-ahead logging) mode** is SQLite's own documented answer — writers append to a separate `-wal` file instead of locking the main database file, so readers aren't blocked by a writer and multiple processes can share one database file correctly, *provided they share a real local filesystem* (SQLite's own documentation is explicit that WAL mode is unreliable over network filesystems like NFS, since it depends on filesystem-level locking primitives those don't implement correctly) — not a concern here, since a Docker named volume lives on the same host as the containers using it, and local dev is obviously local.

Given that, a full client-server database (adding a `postgres` service) would be solving a concurrency problem SQLite's WAL mode already solves for a workload this small (single table, low write frequency, demo scale) — so `src/inventory.py` uses `PRAGMA journal_mode=WAL` with a short-lived connection per call, rather than either a rollback-journal SQLite file (Milestone 1's bug, again) or a new service (over-engineering for the actual load). Verified with a real concurrent-write test before shipping — 8 threads × 10 writes each against one database file, no `database is locked` errors, no lost rows — rather than trusting the documentation alone.
